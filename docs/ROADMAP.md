# Roadmap

## Current candidate: `0.9.0a22`

The source includes a standard-library governance core, bounded cognition, proactive initiative, create-only local autonomy, separately leased workspace inspection, human narrative projections, and optional operator/owner integrations. The candidate is not a claim of completed publication or live deployment; see [PUBLIC_RELEASE.md](../PUBLIC_RELEASE.md).

## Core boundaries retained

- Proposals and conversational interest cannot grant permissions.
- Blocked options never enter exploration; `NO_OP` and `WAIT` remain valid.
- Create-only throughput promotion does not enable new effect classes.
- Root commitments cannot self-ratify changes.
- Verification requires independent evidence, not producer confidence.
- Learned competence is not an authorization credential.

## Optional integration maturity

The [operator integration layer](OPERATOR_INTEGRATIONS.md) and [owner workflows](OWNER_CONNECTION.md) extend the package beyond the original create-only executor. They require explicit host configuration, bounded capabilities, independent outcome checks, and provider-specific acceptance. Their presence is not universal mediation of every Hermes or operating-system action.

The [Firebase control plane](FIREBASE_CONTROL_PLANE.md) is optional. Identity policy, provider configuration, private credentials, rules deployment, and real owner-browser validation remain operator responsibilities. Cloud preferences are requested intent until the relevant host applies and reads back a valid revision.

Private generated-code execution is Linux-specific and fail-closed when Bubblewrap, seccomp, namespace support, or the required Python primitives are absent. No native Windows or macOS sandbox parity is promised.

## Gates before broader release claims

1. Reproduce the full source test suite and record skips honestly.
2. Build wheel and sdist; inspect their public payloads for private material.
3. Verify fresh installed behavior outside the source checkout.
4. Exercise optional SDK tests with the declared extra installed, not only skipped.
5. Validate owner controls, anonymous/outsider denials, stale/replay behavior, and frontend layouts in isolated environments.
6. Verify real provider/cloud effects separately, only with specific operator authorization.
7. Establish documented migration, recovery, revocation, and rollback behavior before stable support.
8. Read back the published tag, artifacts, and educational page before claiming availability.

## Research directions

- Richer evidence-grounded world models and counterfactual calibration.
- More typed adapters with narrow permission and verifier contracts.
- Better human explanations tied to canonical event references.
- Explicit multi-agent coordination protocols rather than inferred consensus.
- Broader portability where security primitives can be preserved, not emulated by weaker checks.

Consciousness claims, universal correctness, autonomous permission expansion, and guaranteed economic returns are not roadmap promises.
